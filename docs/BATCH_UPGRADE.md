# Batch Upgrade — VSM function/ownership improvement intake

**Status:** Organization Control Plane **read-only intake route** proposed under [Organization #307](https://github.com/opensiro/vsm-oss-organization/issues/307). A merged Control Plane entry makes the command discoverable; it does **not** activate an Upstream technical batch executor, select five sources, create a third-party fork/PR, transfer an external harness decision right, or change a canonical assessment.

**Command:** `batch upgrade`. Use the [maintainer Control Plane](AGENT_CONTROL_PLANE.md#batch-upgrade--function-and-ownership-improvement-intake) for dispatch. The owner of any subsequently admitted source-native intervention is [opensiro/upstream](https://github.com/opensiro/upstream), not this Organization repository. This document is an intake/routing contract, not a new Upstream queue, schema, scheduler, assessment procedure or S5 mandate.

## Why this is a distinct question

Existing [`batch upstream`](https://github.com/opensiro/upstream/blob/main/docs/ASSESSMENT_CANDIDATE_BATCHES.md) investigates source-derived native defects and prepares bounded corrective patches. It **does not** aim to change the canonical `A/C/P` classification. The [five-row batch 13](https://github.com/opensiro/upstream/pull/147) produced two native S2 corrective packets but no evidence that the decisive S2 owner/closure changed. The Index command `start a batch assessment` instead evaluates harnesses; it does not propose external product redesign.

`batch upgrade` asks a different, optional engineering question:

> Does an independently verified product need justify changing a VSM function's **first-party decision owner, authority, or feedback closure**, and can the target maintainers safely support that change?

This need not involve any `C → A` transition. A reviewed `C` constructor may already be the intended and better design, and a positive functional improvement may leave the ownership state unchanged.

## Normative and repository boundaries

- [Profile](https://github.com/opensiro/vsm-harness-profile/blob/main/PROFILE.md) owns S1–S5 meaning, function-first mapping, decision-right ownership, closure and the difference between enforcement and discretion.
- [Skills autonomy states](https://github.com/opensiro/vsm-harness-skills/blob/main/skills/assess-vsm-harness/references/autonomy-states.md) own the general assessment notation. `C` requires an established function-specific construction path whose autonomous owner/closure still needs composition; `A` requires a first-party supported mode with an **autonomous agent** owning the decisive function-specific right and closing its feedback loop. **Neither state is a maturity rank or performance score.**
- [Index](https://github.com/opensiro/vsm-harness-index) owns canonical general assessments at pinned source revisions. Only a separately performed, source-first, Skills-conformant assessment can report a new state. Do **not** edit historical frozen vectors or make an Index regrade an Upstream acceptance condition.
- [Upstream #56](https://github.com/opensiro/upstream/issues/56) and its [assessment-to-improvement contract](https://github.com/opensiro/upstream/blob/main/docs/ASSESSMENT_TO_IMPROVEMENT.md) own native fit, contribution evidence and the stage-rights boundary. That contract currently prohibits live model/provider/Browser-agent trials for technical validation.
- An external repository's maintainer owns product scope and acceptance. The current Organization Upstream S1 envelope does not grant a right to publish a new external PR; the legacy finite 34-case Corrective mandate does not transfer to this route.

## Read-only dispatch: `batch upgrade`

1. **Bootstrap and reconcile.** Read current Organization `START_HERE.md`, `docs/ECOSYSTEM.md`, this command contract, Upstream #56/#6, the current Upstream technical batch state, current Index `main` and any active source reservations. The command does **not** borrow a frozen row or silently start a new Upstream batch.
2. **Pin an assessment-derived opportunity.** Inspect the current **included** Index assessment path and exact Index SHA, assessed upstream `review_ref`, declared system-in-focus, function-specific interference/variety, decisive right, current owner, constructor/closure evidence and support/enforcement split. Reinspect the current first-party upstream source before treating any historical finding as live.
3. **Test product desirability.** Identify concrete first-party behavior or maintainer need and evaluate `need`, `mechanism`, `counterfactual` product value and `scope` separately. A `C` label, absent S3/S4, or a possible agent-shaped solution is **not** itself a deficiency. Respect parent/human ownership, resource limits, risk and recoverability.
4. **Describe a falsifiable owner/closure counterfactual.** State `before` and proposed `after` decisions, owner, supported mode, path into subsequent S1 operation, enforcement separate from discretion, and remaining S3/S5/human safeguards. An automated queue, lock, prompt, gate, policy file or CI action does **not** become an agent-owned `A` function just by being added.
5. **Return an evidence-backed intake outcome.** Report `UPGRADE_PROPOSAL`, `NOT_PRODUCT_FIT`, `BLOCKED_EVIDENCE` or `NO_ELIGIBLE_ASSESSMENT_CANDIDATE` as **narrative intake dispositions only**; do not insert these into Upstream's current batch JSON or generated status without an Upstream-owned schema/contract. Record links, blockers and what stage-specific authority would be needed to proceed.

This initial route is **read-only**. It does not implement, allocate or publish a new technical cohort. A full executable multi-candidate mode, frozen-manifest schema, batch size/serial reservation, native script controls and integration/origin states require a **separately reviewed Upstream-owned contract** linked to [#307](https://github.com/opensiro/vsm-oss-organization/issues/307). In particular, do not silently reuse the current `batch upstream` five-row queue or displace parallel operators.

## Future executable technical stage (Upstream-owned)

If separately admitted, apply the current Upstream native-only requirements:

1. Source-pinned product need and an independently established before case.
2. Minimal change demonstrably useful **without** reliance on a desired VSM grade.
3. Matched before/after first-party deterministic tests, negative/null results, safety controls, and no unsupported live LLM/provider/Browser trials.
4. Reviewable OpenSiro handoff; external fork/branch/PR **only with an effective actor- and stage-specific grant**, then real maintainer response.
5. Optional new Index assessment on a **new source ref** after integration, independently adjudicating function, owner and closure; `A` is not presumed.

Track **technical benefit**, **provenance strength**, **external acceptance** and **independent ownership-state observation** as separate dimensions. If useful, a later explicit methodology-controlled comparison can test whether VSM-focused opportunity selection improves defect-finding or functional redesign efficiency against an otherwise matched non-VSM route. Do not claim such a causal effect from one selected cohort.

## Stop and recovery

- Missing exact Index/source evidence, unresolved duplicate reservation, absent maintainer product fit, or unsupported native tests: stop at `BLOCKED_EVIDENCE` or `NOT_PRODUCT_FIT` with the precise reason. No substitute candidate or invented source ref.
- Proposed autonomy transfer without an actual first-party agent owner/closure path: **do not claim `C → A`**.
- Missing external publication mandate: retain an internal technical packet if one is independently authorized; mark any external stage unexercised.
- An issue or pull request without approved Upstream operational ownership is **not** a scheduler item and must not be inserted into `TODO.md`.

**Current return:** a concise, source-linked opportunity assessment and explicit next owning repo/decision. No new autonomy state, S3* audit, S5 mandate, external acceptance, or automatically activated Upstream executor.
