## 3. Proposed mandate — present whole-system discretion, not routine execution

A future effective S3 holder **may consider**, within specifically parent-granted limits, the following *classes of whole-system current decision* when positively grounded in live primary evidence:

1. **Current commitment reconciliation.** When current Organization obligations and one or more S1 execution boundaries cannot jointly be satisfied under current policy, select a documented *present* operating constraint or resolution that S1/S2 cannot validly set alone.
2. **Whole-system resource / priority bargaining.** Select a proportionate current constraint on specifically evidenced shared capacity, deadlines, risk ceilings or binding priority tradeoffs; do **not** invent scarcity from issue counts or decide the roadmap merely because it is visible.
3. **Bounded current accountability / repair.** Where a material cross-boundary evidence/return discrepancy exceeds local S1 decision rights, choose a narrow presently applicable `REQUIRE_REPAIR`, `CONTINUE` or `SET_CONSTRAINT` recommendation, including a named S1 return and expiry.
4. **Claim-assurance exception:** only where the separately [adopted non-operative design #235](https://github.com/opensiro/vsm-oss-organization/pull/235) passes its concrete case test *and* a later valid S5 delegation includes that subject. The general mandate **does not** activate #235 or make this case type automatic.

**Proposed initial allowed response classes for parent-assisted choices:** `CONTINUE`, `SET_CONSTRAINT` for named current commitments, and bounded `REQUIRE_REPAIR`. `STOP`, `SET_RETRY_BUDGET` and `OTHER_CURRENT_CONTROL` require a **separate explicit S5 extension** with source-specific risks and revocation/return rules. Merely including a class in a template is not authorization.

**Prohibited:** Index canonical grades, source pins, evidence acceptance, assessor independence/PR review rules, Skills/Methodology/selected Profile semantics, Awesome's local curation judgments, blanket batch holds, changing the Organization identity/participation boundary, granting new S3 powers, or interpreting S3* findings as final verdicts on Index. Ordinary S1 repair and S2 attenuation must not be reclassified as S3.

## 4. Parent-assisted decision protocol (default proposal)

**Parent-assisted is the selected *target parent-mode operating design*, not itself evidence of the Methodology parent mode `P`.** The agent provides choices; the duly appointed S3 decision owner chooses. The separate base `C` constructor remains composable and does **not** inherit parent authority or an automatic `A` grade. Where `xLagerFeuer` is simultaneously the legitimate S5 parent and *later explicitly appointed* S3 holder, **the role is recorded for each decision**: S5 for identity/mandate/succession and S3 for an admitted *current-control* choice. Sharing a human does not make ordinary S3 into S5.

For each candidate **real** S3 matter, the option-preparing agent must provide one compact packet:

| Field | What the agent supplies before the actual decision |
| --- | --- |
| **Source cut** | Current Organization/Index/Skills/Awesome ref, affected live issue(s), selected Profile/Methodology, evidence confidence |
| **Function and right** | Present whole-system materiality, why S1/S2/S3* cannot decide, exact **effective** grant source and identified S3 decisor |
| **Options** | Usually **A: preserve/CONTINUE**, **B: narrow CONSTRAINT/REPAIR**, **C: bounded alternative or escalate/no-action**; concrete effects, trade-offs and risks, including what happens without intervention |
| **S1 return** | Named S1 work-item target, limited instruction, owner acknowledgement, rollback/expiry or cancellation |
| **Recommendation** | Optional one default with rationale, while alternatives remain independently selectable |
| **Decision receipt** | No prefilled `DECIDED`; wait for explicit decision by appointed holder, then record source and actual response class |

**Execution sequence only after authorization:** `READ_ONLY_SCREEN → OWNER_OPTIONS → OWNER_CHOICE → S3_REQUESTED/DECIDED where legitimately admitted → S1_ACK/APPLIED or explicit rejection/escalation → EFFECT/CLOSED`. The agent may do **read-only screening and packet drafting** without any S3 operational grant; it may not classify that as an S3 transaction. A `REQUESTED` case must satisfy [canonical intake](../../prompts/intake-s3-current-control.md) and [contract](../../contracts/s3/current-control.md) before creating a real transaction. If the parent makes a specific S3 decision directly, cite the S3 role/rights instead of mislabeling it a new S5 event.

**No indefinite approvals by silence.** If unavailable, missing actor authentication, uncertain boundary, or unresolved case evidence, present `ESCALATE / NO_ACTION`; keep the actual intervention unexecuted. Do not misstate a tool comment/CI status as the owner's choice.
