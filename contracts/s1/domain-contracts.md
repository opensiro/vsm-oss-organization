# S1 domain contracts

This file defines the current operational envelopes for the four declared S1 domains of the Opensiro VSM Harness OSS organization.

It applies the selected VSM Harness Profile but does not redefine S1. Repository location alone is insufficient: qualifying work must contribute directly to the declared local operational outcome and remain inside the local authority envelope.

Declared operational S1 domains:

- **Index** — `opensiro/vsm-harness-index`
- **Skills** — `opensiro/vsm-harness-skills`
- **Awesome** — `opensiro/awesome-vsm-harness`
- **Upstream Contributions** — `opensiro/upstream`

`opensiro/vsm-harness-profile` is the normative semantic source. `opensiro/vsm-oss-organization` is the metasystem/control-construction surface. Neither is an operational S1 domain at this recursion.

## Common local contract

Every admitted S1 run declares exactly one domain and uses the executable loop from [`../../roles/S1.md`](../../roles/S1.md). Local variety should remain with that domain whenever it has requisite information and delegated authority. Residual variety must be preserved and escalated rather than silently centralized.

## Index domain

### Durable outcome

Maintain the canonical evidence-backed harness corpus, accepted assessment state, reassessment/provenance history, cohort signatures, and deterministic comparative views.

### Local environment

Public harness repositories and upstream changes; discovery/intake sources; pinned primary evidence; the selected Profile/Methodology contract; canonical assessments and provenance; generated views; validators and generation tooling.

### Local decision rights

Within an admitted Index work item, S1 may decide how to collect/compare primary evidence, apply the selected Methodology, classify candidate duplicate/scope status, resolve repository-relative assessment/reassessment/correction outcomes, update affected canonical surfaces, repair task-local provenance/generation/validation failures, and package a reviewable result.

### Completion evidence

Use the strongest applicable combination of pinned upstream refs, primary evidence links, Methodology-conformant assessment artifacts, corpus/provenance/signature consistency, deterministic generated-view checks, repository validators/tests, and exact final diff/history checks.

### Escalate out of Index S1

Escalate changes to Profile semantics, system-wide Methodology authority, organization identity/scope, cross-S1 authority or whole-system control, security/permissions, licensing policy, or protected/default-branch integration where that right is not separately delegated.

## Skills domain

### Durable outcome

Maintain reusable VSM Harness assessment procedures, skills, references, synchronization/provenance tooling, and deterministic procedure-validation surfaces that apply the selected Profile without redefining it.

### Local environment

Selected Profile semantics/provenance; current assessment procedure implementation; procedure/tooling defects; skill/reference/generated artifacts; validators/tests; downstream procedure consumers.

### Local decision rights

Within an admitted Skills work item, S1 may implement or repair an already-selected procedure, maintain skill/reference/tool consistency, synchronize authoritative upstream Profile artifacts without semantic change, repair provenance/validation/generation failures, add regression coverage for deterministic invariants, and package a reviewable result.

### Completion evidence

Use selected Profile provenance, procedure/reference consistency, repository validators/tests, snapshot/synchronization checks, and exact final diff/version/provenance checks where applicable.

### Escalate out of Skills S1

Escalate Profile semantic change, selection/redefinition of system-wide Methodology authority, cross-S1 decision rights, organization identity/scope, later metasystem decisions, security/permissions, licensing policy, or separately owned integration rights.

## Awesome domain

### Durable outcome

Maintain a curated representative downstream view of organizational forms for the OSS community while keeping canonical assessment facts in the Index.

### Local environment

Current canonical Index corpus; candidate representative forms; editorial evidence about operating domain/organizational distinctiveness/evidence quality/current relevance; community-facing structure; lint and Index-consistency validation.

### Local decision rights

Within an admitted Awesome work item, S1 may decide representative inclusion/presentation under current editorial criteria, organize/narrow sections, describe organizational form without copying canonical assessment state, repair canonical links/format/relationship drift, and package a reviewable result.

### Completion evidence

Use current Index relationships, representative-form evidence, formatting/lint checks, Index-consistency validation, and exact final diff showing canonical assessment facts were not independently redefined.

### Escalate out of Awesome S1

Escalate changes to Index canonical assessment state, Profile/Methodology semantics, organization identity/policy, cross-S1 authority, security/permissions, licensing policy, or separately owned integration rights.

## Upstream Contributions domain

### Durable outcome

Produce, maintain and truthfully report attributable upstream-native interventions to external OSS harnesses: source-backed opportunity selection, native-tested changes, reviewable public contributor-fork/PR packages when authorized, feedback/maintenance, accepted/rejected/blocked outcomes, and provenance-preserving registry/portfolio updates. An intervention may close as evidence-backed `CLOSED_NO_CHANGE` or escalation; external acceptance is not guaranteed.

### Local environment

Third-party OSS repositories and maintainers, current upstream source and contribution rules, issue/PR/review/CI signals, legal/security/CLA/DCO requirements, public OpenSiro contributor forks, optional canonical Index findings, and the Upstream-owned experimental procedures/ledgers.

### Local decision rights

Within an admitted Upstream task, S1 may research and select an opportunity, test product-native fit, prepare scoped source changes using native deterministic script/CLI checks, maintain OpenSiro's own evidence/registry, triage external feedback and perform ordinary locally authorized correction/recovery. GitHub writes to forks or external PRs require a **separate effective actor, provider permission, exact-stage grant and applicable third-party rules**. The historic finite Corrective cohort is not a standing permission for future unrelated work.

### Completion evidence

Use pinned first-party source/issue/PR refs, before/after native behavior when relevant, exact source/branch/test/provenance receipts, authenticated external lifecycle readback, preserved negative outcomes, attributable decisions, policy gates, and escalation/maintenance evidence. A merged third-party PR proves that disposition, not deployed-user benefit, causal VSM effect or autonomous S1 ownership.

### Escalate out of Upstream S1

Escalate external maintainer acceptance/merge/assignment, permissions or unreached grant, CLA/DCO/legal/security decisions, third-party policy exceptions, cross-domain authority, normative Profile/Skills/Index interpretation, experimental fit-metric policy migration, system boundary/identity changes and generalized publication mandates. Never issue third-party comments/PRs, merge or alter repository settings from S1 designation alone.

## Evidence boundary

The existence and exercise of these domain contracts establishes operational construction/evidence paths. It does **not** by itself establish `S1=A` or another publication state. Formal ownership classification remains governed by the selected Profile/Methodology and concrete operating-mode evidence.

Representative operational evidence is recorded under [`../../records/s1/autonomy-coverage.md`](../../records/s1/autonomy-coverage.md).
